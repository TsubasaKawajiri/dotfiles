# コミットポリシー / 作業の進め方

Claude は作業する際、以下のルールに従って変更内容を分割・コミットしてください。

## 1. 作業の分割ルール

- 大きな機能を一度に実装せず、**小さなサブタスクに分解**してから作業を開始すること。
- 新しい依頼を受けたときは、まず最初に「今回の変更をどのサブタスクに分けるか」を箇条書きで示してください。
  - 例:
    - [ ] 保存成功時の toast を実装
    - [ ] toast 表示のテストを追加・更新
    - [ ] 画面レイアウトの調整・フィールドの編集 UI 実装
- サブタスクは **一つずつ順番に完了**させてください。
- 各サブタスクが完了したタイミングで、**そのサブタスクだけを含むコミット** を行ってください。

## 2. コミットの分け方

1 つのコミットに含める変更は、**1 種類の目的に絞る**ようにしてください。  
以下のような変更は、必ずコミットを分けてください。

- UI の変更 / レイアウト調整
- ビジネスロジックの追加・修正
- テストの追加・更新
- リファクタリング（振る舞いを変えないコード整理）

### 具体例: アラート詳細画面の改善

「アラート詳細画面で保存時に toast を出して、テストを書いて、画面も少し直す」というケースでは、次のように分割します。

1. **Commit 1: toast の実装**
   - 内容:
     - 保存成功時に表示する toast を実装
     - UI コンポーネントや hooks の追加など、toast 機能に必要な最小限の変更のみ
   - メッセージ例:
     - `feat(alerts): show toast on successful alert update`

2. **Commit 2: テストの追加・更新**
   - 内容:
     - toast 表示に関するテストの追加・更新
     - テストヘルパーの微調整が必要な場合はこのコミットに含めてもよい
   - メッセージ例:
     - `test(alerts): add tests for alert update toast`

3. **Commit 3: 画面レイアウト・編集 UI の調整**
   - 内容:
     - ステータス / 対応内容 / 担当者の編集フィールド追加・レイアウト変更
     - バインド・フォーム回りの変更
   - メッセージ例:
     - `feat(alerts): make alert detail fields editable`

4. （必要なら）**Commit 4: リファクタリング**
   - 内容:
     - コンポーネント分割、命名変更など振る舞いを変えない改善
   - メッセージ例:
     - `refactor(alerts): extract alert detail form component`

## 3. コミットメッセージ

- 可能であれば **Conventional Commits** に近い形式を使ってください。
- 接頭辞の例:
  - `feat:` 新機能・画面の追加
  - `fix:` バグ修正
  - `refactor:` 振る舞いを変えないリファクタ
  - `test:` テストの追加・修正
- スコープとして、対象機能やドメインを括弧で指定してください。
  - 例:
    - `feat(alerts): show toast on successful alert update`
    - `test(auth): add tests for session fetch error`

`wip` のような意味の曖昧なメッセージは使用しないでください。

## 4. TDD との関係

- すでに定義されている **TDD ワークフロー（レッド → グリーン → リファクタ）** はそのまま守ってください。
- 1 つのサブタスク（例: toast 実装）について、
  - そのサブタスクに必要なテストを追加
  - テストを失敗させる
  - 実装してテストを通す
  - 必要なリファクタを行う
  - → ここまでを 1 単位として、**1 コミットに収まるようにコードを提示**してください。
- テスト専用のコミットを分けたい場合は、上記の「テストの追加・更新」のように、  
  「テストのみを変更するサブタスク」として切り出してください。
