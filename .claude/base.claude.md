# Claude 基本方針（base.claude.md）

このファイルは「会話・回答・実装全般」の基本方針を定義する。
タスク粒度の分割ルールはこのファイル、コミット単位の分割は `workflow-commit.md`、
TDD ワークフローは `workflow-tdd.md` で扱う。

---

## 1. 代替案の提示

- ユーザーがバッドプラクティスを選択しようとしている、または他により適切なアーキテクチャ・手法が考えられる場合は、代替案を提示する。
  - 例: キューイング処理の自前実装 → マネージドサービス（SQS / Cloud Tasks 等）、独自の認証実装 → IdP（Auth0 / Cognito 等）
  - Why: ユーザーが知識不足や思考の固定化により意図せず悪い方向に進んでいる場合があり、AI による代替案提示が早期軌道修正の機会になるため。

---

## 2. コード生成の基本ルール

- 詳細コードより先に「変更範囲・影響箇所・方針案」を整理して提示する。
  - Why: 方針合意なしに実装に入ると手戻りが発生するため。

- 動作に必要な前提（環境変数・型定義・補助関数・import 等）を一緒に提示する。
  - Why: 提示コードを単体で動かせる状態にし、ユーザーが「動かない」原因調査に時間を使わずに済むため。

- 必要最小限の構造で実装する。余計な抽象化はしない。
  - Why: 過剰抽象化は読みづらさと変更コストを増やすため。

---

## 3. 設計・建築的判断の原則

- UI / ビジネスロジック / DB / バリデーション / 認証 を1つのファイル・関数に混在させない。
  - Why: 単一責務に保つことで、変更時の影響範囲を限定できるため。

- 再利用性・拡張性・テスト容易性の観点で構造を提案する。必要なら責務分割・抽象化を提案する。
  - Why: 後から構造を変えるコストは初回の設計コストより遥かに高いため。

- 設計判断には「なぜそうするか」を短く添える。
  - Why: ユーザーが判断の妥当性を評価し、別案を提示できるようにするため。

- 不変であるべき値は言語機能でイミュータブル化する。
  - 例: Ruby `.freeze` / TypeScript `as const`・`readonly` / Python `Final`
  - 対象: グローバル定数・設定値・列挙値
  - Why: 意図しない変更を防ぎ、バグの混入経路を1つ減らすため。

## 4. ユーザーとの共同作業ルール

**このセクションの「分割」はタスク・会話レベルの整理を指す。コミット単位の分割は `workflow-commit.md` を参照。**

- 大きめの開発依頼は最初に TODO リストへ分割して提示し、1つずつ順番に完了させる。
  - Why: 全部同時に進めると差分が大きくなり、レビュー・修正が困難になるため。

- 作業開始前に以下を整理する：目的 / 前提 / 制約 / 作業範囲 / 出力形式。
  - Why: 認識ズレを実装後ではなく開始前に検出するため。
