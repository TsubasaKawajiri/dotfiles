# TDD開発ワークフロー指針
TDD（テスト駆動開発）を実施する際は、以下の原則と手順を遵守してください。

## 基本原則

1. **レッド → グリーン → リファクタ** の TDD サイクルを常に守る。
2. テストを先に書き、失敗することを確認してから実装を行う。
3. テストをパスさせるために必要な最小限の変更のみを加える。
4. すべてのテストがパスした状態でのみリファクタリングを行う。
5. **指示が不明確な場合や複数の実装方法が考えられる場合は、実装前にユーザーに確認すること。**
6. **テストコードの量はプロダクトコードより多くなることを厭わない。** テスト対コード比が高いほど品質・保守性が上がる。

## 開発フロー

### 1. テストの作成

- 新機能やバグ修正の要件を満たすテストを作成する。
- テスト名は日本語で表現し、期待される挙動を明確に記述する。
- テストを実行し、期待通り失敗することを確認する。

### 2. 実装の追加

- 失敗したテストをパスさせるために必要な最小限のコードを実装する。
- 過剰な機能追加や設計変更は行わない。
- すべてのテストがパスすることを確認する。

### 3. リファクタリング

- すべてのテストがパスした状態で、以下の観点からコードを改善する：
  - 可読性
  - 再利用性
  - テスト容易性
- リファクタリング後もすべてのテストがパスすることを確認する。

## テスト実行の例外ケース

以下のような修正の場合は、テストの実行をスキップできます：

- AI 指示ドキュメント（`CLAUDE.md`、`AGENTS.md` など）の修正
- README ファイルの修正
- コメントのみの追加・修正
- ドキュメントファイル（`.md`）の追加・修正
- 設定ファイルのフォーマット修正（機能変更を伴わない）

ただし、これらの修正であっても、以下の場合はテストを実行してください：

- 複数の種類のファイルを同時に修正している場合
- 設定ファイルの機能変更を伴う修正の場合
