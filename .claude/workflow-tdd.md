# TDD 開発ワークフロー（workflow-tdd.md）

このファイルは TDD（テスト駆動開発）のサイクルとテスト実行例外を定義する。
コード品質・設計の一般方針は `base.claude.md`、コミット粒度は `workflow-commit.md` を参照。

---

## 1. TDD サイクル

「**レッド → グリーン → リファクタ**」を1単位として進める。

- **レッド**: 新機能・バグ修正の要件を満たすテストを先に書き、実行して失敗することを確認する。
  - テスト名は日本語で「期待される挙動」を明確に記述する。
  - 複数のテストケースを書く場合、グリーンに進む前にテスト一覧（ケース名）を提示し、過不足をユーザーに確認する。
  - Why: テストが期待通り落ちることを確認しないと、テスト自体が無効でも気付けないため。
  - Why: テストケースの網羅性は実装後では遡及確認が困難で、レッド段階での確認がもっとも安価なため。

- **グリーン**: そのテストをパスさせる最小限のコードのみ実装する。過剰な機能追加・設計変更はしない。
  - Why: 最小実装に絞ることで、変更とテストの対応関係を保つため。

- **リファクタ**: 全テストがパスした状態で、可読性・再利用性・テスト容易性の観点で改善する。改善後も全テストパスを再確認する。
  - Why: グリーン状態でないとリファクタの安全網がなく、振る舞い変更を検出できないため。

---

## 2. 補足ルール

- 指示が不明確な場合や複数の実装方法が考えられる場合は、実装前にユーザーに確認する。
  - Why: TDD は「何をテストするか」が決まらないと開始できないため。

---

## 3. テスト実行をスキップしてよいケース

以下の修正は、テスト実行を省略してよい：

- AI 指示ドキュメント（`CLAUDE.md`、`AGENTS.md` 等）の修正
- README の修正
- コメントのみの追加・修正
- ドキュメントファイル（`.md`）の追加・修正
- 機能変更を伴わない設定ファイルのフォーマット修正

ただし、以下に該当する場合はスキップせずテストを実行する：

- 複数種類のファイルを同時に修正している場合
- 設定ファイルの機能変更を伴う修正

Why: 上記対象はテストで担保される振る舞いを変えないため省略可能。一方、混在修正・機能変更時はテスト対象が含まれる可能性が高いため省略しない。
